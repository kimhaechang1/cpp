# UDP (User Datagram Protocol) - "던지고 잊는" 실시간 통신

## 1. 샌드위치 상황: "왜 TCP로는 렉(Lag)을 잡을 수 없는가?"
당신은 실시간 FPS 게임의 서버 개발자입니다. 64명의 플레이어가 0.01초마다 위치 데이터를 주고받습니다.
- **TCP의 문제**: 중간에 패킷 하나가 유실되면, TCP는 신뢰성을 위해 그 패킷을 재전송받을 때까지 이후에 도착한 최신 패킷들을 모두 큐에 쌓아두고 앱에 전달하지 않습니다 (**Head-of-Line Blocking**).
- **결과**: 플레이어 입장에서는 0.1초 전의 과거 위치를 기다리느라 현재의 화면이 멈추는 '렉'을 경험하게 됩니다.
- **UDP의 해법**: "유실됐어? 상관없어. 그냥 다음 최신 패킷을 바로 보여줘!"

---

## 2. UDP의 핵심 특징 (TCP vs UDP)

| 특징 | TCP (Stream) | UDP (Datagram) |
| :--- | :--- | :--- |
| **연결 방식** | 3-Way Handshake (전화 연결) | No Connection (우편물 투척) |
| **데이터 경계** | 없음 (바이트의 흐름) | **있음 (메시지 단위, 1 Send = 1 Recv)** |
| **신뢰성** | 재전송, 순서 보장, 흐름 제어 | **없음 (Best-effort)** |
| **속도** | 상대적으로 느림 (오버헤드 큼) | **매우 빠름 (헤더 단 8바이트)** |
| **용도** | 로그인, 인벤토리, 채팅 | **캐릭터 이동, 보이스 채팅, 스트리밍** |

## 3. Winsock에서의 UDP API

### 3.1 소켓 생성
UDP 소켓은 타입을 `SOCK_DGRAM`으로, 프로토콜을 `IPPROTO_UDP`로 설정합니다.
```cpp
SOCKET udpSocket = socket(AF_INET, SOCK_DGRAM, IPPROTO_UDP);
```

### 3.2 데이터 보내기 (`sendto`)
TCP의 `send`와 달리, 매번 **누구에게(To)** 보낼지 목적지 주소를 함께 넘겨야 합니다.
```cpp
int sendto(
    SOCKET s,
    const char* buf,
    int len,
    int flags,
    const sockaddr* to, // 목적지 주소
    int tolen
);
```

### 3.3 데이터 받기 (`recvfrom`)
누가 보냈는지 **누구로부터(From)** 왔는지 주소 정보를 함께 받아옵니다.
```cpp
int recvfrom(
    SOCKET s,
    char* buf,
    int len,
    int flags,
    sockaddr* from, // 보낸 사람의 주소를 담을 공간
    int* fromlen
);
```

## 4. 핵심 질문 답변 (Q&A Deep Dive)

### Q1. 상대방 소켓이 닫혀있을 때 `sendto`를 하면?
UDP는 비연결형이므로 `sendto`는 패킷을 내보내는 즉시 성공을 반환합니다. 상대방의 수신 여부는 확인하지 않습니다. 단, 윈도우에서는 이후 `recvfrom` 호출 시 `WSAECONNRESET` 에러를 통해 간접적으로 알 수도 있지만, 기본적으로는 **"성공을 보장하지 않는다"**고 생각해야 합니다.

### Q2. UDP도 `bind`가 필요한가요?
- **수신자(Server)**: 필수입니다. 특정 포트로 들어오는 패킷을 낚아채야 하기 때문입니다.
- **송신자(Client)**: 선택입니다. `bind`를 안 하면 OS가 무작위 포트를 할당합니다.

### Q3. 데이터 경계 (100바이트 3번 보내기 테스트)
TCP와 달리 UDP는 **Datagram(데이터 덩어리)** 단위로 관리됩니다.
- 송신: `sendto(100)`, `sendto(100)`, `sendto(100)`
- 수신: `recvfrom(300)`을 **한 번** 호출하면? -> **100바이트만 읽힙니다.**
- 나머지 데이터는 다음 `recvfrom` 호출을 위해 OS 수신 버퍼에 대기합니다. 즉, **보낸 횟수와 받는 횟수가 반드시 일치**해야 합니다.

### Q4. 헤더(UDPHdr)를 우리가 만드나요?
아니요, OS가 자동으로 붙여줍니다. 제가 언급한 이유는 **오버헤드(배보다 배꼽이 더 큰 상황)**를 설명하기 위함입니다.
- TCP 헤더: 최소 20바이트 (신뢰성을 위한 각종 장치 포함)
- UDP 헤더: **딱 8바이트** (출발/도착 포트, 길이, 체크섬 끝!)
실시간 이동 데이터(약 4~12바이트)를 보낼 때 TCP는 배보다 배꼽이 더 커서 네트워크 대역폭을 낭비하게 됩니다.

## 5. 하드웨어 및 프로토콜 검증 (Visualizing UDP)
UDP는 데이터의 **경계(Boundary)**를 유지합니다. 
만약 송신 측에서 `sendto`를 100바이트씩 3번 호출했다면, 수신 측에서도 정확히 `recvfrom`을 3번 호출해야 3개의 메시지를 온전히 받습니다. (TCP처럼 300바이트를 한 번에 긁어오는 것이 불가능합니다.)

### 🔬 검증 포인트
1. `sizeof(UDPHdr)`: UDP 헤더는 단 **8바이트**입니다. (TCP는 기본 20바이트 + 옵션)
2. **MTU (Maximum Transmission Unit)**: 보통 1500바이트를 넘기면 네트워크 계층에서 쪼개지므로, UDP 패킷은 보통 1472바이트(1500 - IP 20 - UDP 8) 이내로 구성하는 것이 국룰입니다.

## 6. 심화: Connected UDP (`connect()` 호출)
UDP 소켓에도 `connect()`를 호출할 수 있습니다. 하지만 TCP와는 본질적으로 다릅니다.

### 6.1 작동 원리
- **No Handshake**: 네트워크 통신이 전혀 발생하지 않습니다.
- **Local State**: 내 OS 커널에 "이 소켓의 목적지 주소를 고정하겠다"고 등록만 합니다.

### 6.2 왜 사용하는가?
1. **API 단순화**: `sendto` 대신 `send()`, `recvfrom` 대신 `recv()` 사용 가능 (주소 인자 생략).
2. **성능(Performance)**: `sendto` 호출 시마다 발생하는 내부적 주소 등록/해제 과정을 생략하여 속도가 향상됩니다.
3. **에러 피드백**: 상대방이 소켓을 열지 않아 발생하는 ICMP 포트 에러를 다음 `recv` 시점에서 명확히 감지할 수 있습니다.
