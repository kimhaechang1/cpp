## 1. `std::string_view` (C++17) : 무거운 문자열 대신 유리창 달기

`std::string`은 매우 편리하지만 내부적으로 **동적 할당(Heap Memory)**을 사용합니다. 문자열을 반환하거나 매개변수로 넘길 때 `std::string`을 값으로 전달하면, 운영체제에 메모리를 새로 요청하고 문자열을 복사하는 무거운 작업이 발생합니다.

`std::string_view`는 이름 그대로 **"문자열을 바라보는 창문(View)"**입니다.
* **구조**: 내부적으로 딱 두 가지 데이터만 가집니다. `const char*` (시작 주소) + `size_t` (길이). 즉 우리가 직접 만든 `PayloadView`와 완벽히 똑같은 원리입니다!
* **장점**: 메모리 할당이 **0(Zero)**입니다. `std::string`이나 `char 배열`을 가리키기만 하므로 복사 비용 없이 즉시 반환하고 전달할 수 있습니다.
* **주의점**: 원본 데이터가 파괴된 후에도 뷰를 들고 있으면 댕글링 포인터(허상 참조)가 됩니다. 원본의 수명이 더 길 때만 사용해야 합니다.

## 2. `reserve()` vs `resize()` : 공간만 찜할 것인가, 입주까지 시킬 것인가?

이 둘은 성능 최적화의 핵심이며 초보자들이 가장 많이 헷갈리는 개념입니다.

### `reserve(N)` (공간 예약)
* **의미**: "나중에 쓸 수도 있으니 메모리 공간(Capacity)만 `N`만큼 미리 확보해 둬."
* **상태**: 공간은 확보했지만 **실제 크기(Size)는 여전히 0**입니다. 요소가 아직 없습니다.
* **언제 쓰나?**: 앞으로 `push_back()`이나 `insert()`를 수없이 많이 할 예정일 때, 중간에 메모리가 부족해서 이사(재할당)가는 오버헤드를 막기 위해 씁니다.

### `resize(N)` (크기 변경 및 초기화)
* **의미**: "지금 당장 크기(Size)를 `N`으로 늘리고, 빈자리는 0(기본값)으로 꽉 채워 넣어."
* **상태**: 크기가 `N`이 되며, 인덱스(`vec[0]`, `vec[3]`)로 즉시 접근할 수 있습니다.
* **언제 쓰나?**: 네트워크 `recv()` 함수처럼, **운영체제에게 "여기 빈 버퍼 1024바이트가 있으니 여기에 데이터를 덮어써줘!"**라고 넘겨줄 때 씁니다.

## 3. 구조체를 통째로 직렬화 / 역직렬화 하는 방법

지금까지는 `WriteInt`, `WriteFloat` 처럼 필드 단위로 하나씩 직렬화했습니다. 하지만 C++은 메모리를 직접 다룰 수 있으므로, 구조체 덩어리를 통째로 바이트 배열로 캐스팅할 수도 있습니다.

```cpp
// [직렬화] 구조체를 통째로 바이트 배열로 밀어넣기
PlayerInfo pInfo = { ... };
std::vector<uint8_t> buffer(sizeof(PlayerInfo));
std::memcpy(buffer.data(), &pInfo, sizeof(PlayerInfo));

// [역직렬화] 바이트 배열에 구조체 포인터를 씌워서 그대로 읽기
PlayerInfo* pRecovered = reinterpret_cast<PlayerInfo*>(buffer.data());
```
**하지만 왜 필드 단위 직렬화를 추천할까요? (위험성)**
1. **메모리 패딩(Padding)**: 컴파일러는 최적화를 위해 구조체 멤버 사이에 빈 공간(더미 바이트)을 넣습니다. 이 쓰레기값까지 네트워크로 전송되면 대역폭 낭비와 보안 취약점이 생깁니다.
2. **포인터 위험**: 구조체 안에 `std::string`이나 포인터(`*`)가 있다면, 통째로 복사해봤자 실제 데이터가 아닌 '주소값'만 전송됩니다. 수신 측에서는 쓰레기 메모리 주소가 됩니다.
3. **엔디안(Endianness)**: 서로 다른 CPU(예: 인텔 vs ARM) 간 통신 시, 통째로 복사하면 바이트 순서가 뒤집혀서 값이 완전히 박살납니다.

따라서 고품질 서버에서는 구조체를 통째로 복사하는 것을 지양하고, **직렬화 함수를 통해 한 필드씩 엔디안을 맞추어 버퍼에 밀어넣는 것**이 정석입니다.

## 4. 추가 아키텍처 피드백 (Map 탐색 최적화)

질문자님이 놓친 사소하지만 중요한 성능 포인트가 하나 더 있습니다! 
`SessionManager.cpp`의 코드를 보겠습니다.

```cpp
// 현재 코드
if (this->userSessionMap.contains(id)) {
    return userSessionMap[id].first; // ⚠️ 탐색이 2번 발생합니다!
}
```
* **문제점**: `contains(id)`로 해시 테이블을 한 번 뒤져서 찾았는데, `[id]` 연산자를 쓰면서 다시 해시를 계산하고 테이블을 또 뒤집니다. 초당 수만 번 호출되면 아까운 CPU 낭비입니다.
* **해결책**: `find()`를 사용하면 한 번에 끝납니다!

```cpp
// 개선된 코드 (단일 탐색 패턴)
if (auto it = this->userSessionMap.find(id); it != this->userSessionMap.end()) {
    return it->second.first; // 이미 찾은 노드의 주소(it)에서 곧바로 빼옵니다.
}
return std::nullopt;
```

## 5. 순환 참조 (Circular Dependency) 요약
* **증상**: "A가 B를 알고, B가 A를 알아야 하는 상황"에서 컴파일러가 "알 수 없는 타입"이라며 뻗어버림.
* **해결**: 헤더를 무작정 `#include` 하지 말고, **전방 선언(`enum class Type;` 또는 `class Name;`)**을 활용해 "이런 타입이 존재한다"고만 알려준 뒤, 얽힌 구조체를 독립적인 파일(`ByteSerializer.h`)로 빼내어 의존성을 단방향 나무뿌리 형태로 정리합니다.
