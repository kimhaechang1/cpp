# 부록: std::unordered_map의 고성능 탐색 및 삭제 전략

이 문서는 모던 C++ 게임 서버 및 고성능 백엔드 아키텍처 환경에서 `std::unordered_map`을 사용할 때 발생하는 탐색 및 삭제 오버헤드의 아키텍처적 원리와, 멀티스레드 환경에서의 안전한 동기화 전략을 다룹니다.

---

## 🚦 1. 핵심 쟁점: erase(key) vs erase(iterator)

`std::unordered_map`에서 요소를 제거하는 방식은 크게 두 가지 오버로딩 함수로 나뉩니다.

```cpp
// 1. Key를 던져 지우는 방식
_sessionMap.erase(clientSocket);

// 2. Iterator(반복자 주소)를 던져 지우는 방식
auto it = _sessionMap.find(clientSocket);
if (it != _sessionMap.end()) {
    _sessionMap.erase(it);
}
```

이론적으로 두 방식은 동일하게 요소를 삭제하지만, **시간 복잡도와 CPU 연산 과정에서 미세하지만 결정적인 성능 차이**가 발생합니다.

---

## 🔍 2. 두 방식의 CPU 연산 흐름 상세 비교

### 🔴 A. erase(key)의 내부 동작 (2중 연산 발생)
삭제하기 전에 해당 요소의 존재 여부를 먼저 확인하기 위해 `find`를 호출하고 연이어 `erase`를 호출하면, 컴파일러와 CPU는 독립적인 두 함수 호출 간에 어떠한 기억도 공유하지 않습니다. (C++의 Statelessness 철학)

1. **`find(key)` 실행 시**:
   * 키의 해시값 계산 (해싱 오버헤드)
   * 해시 테이블의 특정 버킷(Bucket) 매핑
   * 버킷 내부 연결 리스트를 타며 동치성 비교(`==`)를 거쳐 노드 탐색
   * 탐색 성공 후 노드 주소(`it`) 반환
2. **`erase(key)` 실행 시 (중복 연산)**:
   * 맵 라이브러리는 앞서 `find`가 실행되었었는지 알지 못하므로, 키의 해시값을 **처음부터 다시 계산**
   * 버킷 매핑 **또 실행**
   * 연결 리스트를 돌며 동치성 비교(`==`)로 노드 **또 탐색**
   * 발견 후 노드 삭제 및 해제

> [!WARNING]
> 문자열(`std::string`)을 Key로 사용하는 맵의 경우, 문자열 해싱 연산과 문자열 대조 비교(`strcmp`)가 2번 중복 실행되면서 초당 수만 건을 다투는 게임 루프에서 심각한 병목을 유발합니다.

### 🟢 B. erase(iterator)의 내부 동작 (지름길 직행)
이미 `find`를 통해 찾아낸 물리적 메모리 주소표(반복자 - Iterator)를 삭제 함수에 직접 전달하는 방식입니다.

1. **`find(key)` 실행 시**:
   * 위와 동일하게 단 1회의 정상적인 해시 계산과 탐색을 거쳐 물리적 노드 주소(`it`)를 획득합니다.
2. **`erase(iterator)` 실행 시**:
   * 맵은 이미 물리적 노드 주소를 쥐고 있으므로 **다시 해싱 연산을 하거나 비교 연산을 돌릴 필요가 전혀 없습니다.**
   * 주소지로 다이렉트로 직행하여 연결 리스트의 링크만 끊어내고 즉시 메모리를 해제합니다.
   * 연산 횟수가 **절반(1회)으로 단축**되어 극단적으로 효율적입니다.

---

## ⚡ 3. 그렇다면 왜 erase(key)가 존재하고 사용될까요?

`erase(iterator)`가 성능과 원리 면에서 완벽한 상위 호환임에도 불구하고 `erase(key)`가 널리 쓰이는 이유는 **두 가지 치명적인 트레이드오프** 때문입니다.

### 🛡️ 이유 A: 반복자 무효화(Iterator Invalidation)와 서버 크래시 방지
멀티스레드 비동기 서버 환경에서 가장 공포스러운 버그 중 하나는 **"내가 구한 주소표가 지우기 직전에 썩어버리는 현상"**입니다.

1. **상황 발생**: 스레드 A가 `find`를 호출하여 특정 노드 주소(`it`)를 쥐고 락을 일시 해제했거나 비동기 콜백을 대기합니다.
2. **사고 발생**: 그 찰나의 순간에 다른 스레드가 맵의 요소를 삽입/삭제하여 맵 내부가 재배열(Rehash)되거나, 해당 노드가 먼저 지워집니다.
3. **참사 발생**: 스레드 A가 쥐고 있던 `it`는 이미 파괴된 메모리를 찌르는 **허상 포인터(Dangling Iterator)**가 되며, 이 썩은 반복자를 가지고 `erase(it)`를 찌르는 순간 **서버는 예외를 뱉고 즉시 크래시(Crash - Segmentation Fault)로 다운**됩니다.
4. **안전장치**: 반면, `erase(key)`는 비록 다시 연산하는 오버헤드가 있더라도, **삭제를 수행하는 바로 그 시점의 상태를 기준으로 실시간 재해싱을 돌려 안전함이 검증된 대상만 지우기 때문에** 반복자 무효화로 인한 서버 다운 사고로부터 100% 안전합니다.

### ✍️ 이유 B: 압도적인 코드 가독성과 생산성
단순히 "있으면 지우고 없으면 무시하라"는 로직을 구현할 때, 두 방식의 가독성 차이는 매우 큽니다.
* **`erase(iterator)` 방식 (4줄)**: `find` -> `if(it != end)` 분기 -> `erase(it)` 실행.
* **`erase(key)` 방식 (1줄)**: `_sessionMap.erase(key);` (지워졌다면 `1`, 없었다면 `0` 반환값까지 우아하게 반환하여 분기 처리 연동이 쉬움).

---

## 📊 4. 실무 선택 가이드라인

C++의 철학은 **"개발자가 상황에 맞게 최선의 무기를 고르게 하는 것"**입니다. 게임 개발자는 상황에 맞춰 무기를 다르게 쥐어야 합니다.

1. **락 영역이 완벽히 묶여 있고, 검색 즉시 삭제가 일어나는 고성능 메인 프레임 루프**:
   * 반복자가 오염될 위험이 0%이므로, 성능 극대화를 위해 무조건 **`erase(iterator)`** 방식을 고수합니다. (비효율적인 `erase(key)`를 피함)
2. **비동기 콜백 패턴, 락의 범위가 쪼개져 있는 다중 스레드 연동부**:
   * 반복자가 무효화되어 서버가 터지는 끔찍한 버그를 방지하고 시스템 안정성을 최우선으로 확보하기 위해 안전벨트인 **`erase(key)`**를 채택합니다.
3. **가독성과 단순 삭제가 중요하고 성능 체감이 적은 보조 로직**:
   * 코드 생산성을 극대화하기 위해 **`erase(key)`** 한 줄로 명료하게 마감합니다.
