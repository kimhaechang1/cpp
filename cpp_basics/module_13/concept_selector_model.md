## 💡 I/O Multiplexing (다중 입출력)

**"하나의 창구에서 여러 명의 고객을 동시에 감시할 수는 없을까?"**

I/O 멀티플렉싱은 하나의 스레드가 여러 개의 소켓을 동시에 관리하는 기술입니다.
가장 대표적이고 전통적인 함수가 바로 **`select()`** 입니다.

### 🔄 Blocking vs Non-Blocking
* **Blocking (블로킹)**: 함수를 호출하면, 결과가 나올 때까지 제어권을 OS에 넘기고 **스레드는 대기 상태(Sleep)** 에 빠집니다. (예: 기존의 `recv`, `accept`)
* **Non-Blocking (논블로킹)**: 함수를 호출하면, 데이터가 없어도 즉시 리턴하여 **스레드가 다른 일을 계속**할 수 있게 합니다.

`select()` 모델은 **여러 소켓 중 "어떤 소켓이 현재 Non-Blocking 상태로 즉시 데이터를 읽거나 쓸 수 있는지" OS에게 물어보는 방식**입니다.

---

## 🛠️ 핵심 원리: `fd_set` 과 관찰자

`select()`를 사용하려면 **관찰할 소켓들의 목록**을 만들어야 합니다. 이를 **`fd_set`** (File Descriptor Set)이라고 부릅니다.

### 1. `fd_set`의 정체 (Windows vs Linux)
* **Linux**: `fd_set`은 거대한 **비트마스크(Bitmask)** 입니다. (예: 3번 소켓을 감시하려면 3번째 비트를 1로 켬)
* **Windows (Winsock2)**: `fd_set`은 소켓들의 **배열**입니다. 내부에 배열 요소 개수를 나타내는 `fd_count`와 실제 소켓 배열인 `fd_array`를 가집니다.

### 2. `fd_set`을 다루는 매크로 (Macro)
C++에서는 직접 `fd_set`을 조작하지 않고 매크로 함수를 사용합니다.

* `FD_ZERO(&set)`: 관찰 목록(`set`)을 완전히 비웁니다. (초기화)
* `FD_SET(socket, &set)`: 관찰 목록에 특정 `socket`을 **추가**합니다.
* `FD_CLR(socket, &set)`: 관찰 목록에서 특정 `socket`을 **제거**합니다.
* `FD_ISSET(socket, &set)`: (select 호출 후) 해당 `socket`에 **변화가 발생했는지(이벤트가 있는지) 확인**합니다.

## 🚦 `select()` 함수의 동작 메커니즘

`select()` 함수는 3가지 종류의 이벤트 목록(`fd_set`)을 OS에게 넘겨주고, 상태 변화가 일어날 때까지 기다립니다.

```cpp
int select(
    int nfds,           // (Windows에서는 무시됨. 호환성을 위해 0 전달)
    fd_set* readfds,    // 수신(Read) 가능한 소켓 목록 (recv, accept 대상)
    fd_set* writefds,   // 송신(Write) 가능한 소켓 목록 (send 대상)
    fd_set* exceptfds,  // 예외(Exception)가 발생한 소켓 목록
    const timeval* timeout // 타임아웃 (얼마나 기다릴지. NULL이면 무한 대기)
);
```

### ⚙️ 동작 순서
1. **목록 작성**: `readfds` 에 감시할 소켓들을 `FD_SET`으로 쑤셔 넣습니다.
2. **OS에 전달**: `select()` 호출. OS가 소켓들을 감시합니다.
3. **이벤트 발생**: 누군가 데이터를 보냈거나(recv), 새로운 접속(accept)이 들어오면 `select()`가 리턴됩니다.
4. **결과 확인**: OS는 넘겨준 `readfds` 배열을 조작하여, **이벤트가 발생하지 않은 소켓들은 배열에서 지워버립니다.** 즉, 살아남은 소켓들만 `FD_ISSET`으로 찾아내어 처리합니다.

---

## 📉 왜 `select()`는 구형 취급을 받을까? (2025 아키텍처 관점)

1. **매번 복사해야 하는 오버헤드**: `select()`가 호출될 때마다 우리가 만든 `fd_set` 배열을 **OS 커널 영역(Kernel Space)으로 매번 복사(Copy)** 해야 합니다.
2. **배열 덮어쓰기**: 함수가 끝나면 OS가 원본 `fd_set`을 수정해버리기 때문에, 루프를 돌 때마다 `fd_set`을 처음부터 다시 세팅(`FD_ZERO`, `FD_SET`)해야 합니다.
3. **O(N) 탐색**: 이벤트가 발생해도 정확히 누가 발생시켰는지 안 알려줍니다. 남은 소켓들을 처음부터 끝까지 `for`문으로 돌면서 `FD_ISSET`으로 하나하나 찔러봐야 합니다.

**👉 결론**: `select()`는 수천 개의 접속을 처리하기엔 너무 무겁습니다. 하지만 이 모델의 한계를 알아야 나중에 배울 궁극의 비동기 모델 (Windows **IOCP** / Linux **epoll**)의 위대함을 뼈저리게 이해할 수 있습니다!

## ❓ Q&A 및 업데이트 내역

**Q. 감시할 소켓이라는 게 서버의 Listen 소켓을 말하나요, 아니면 통신용 Client 소켓들을 말하나요?**
**A. 정답은 "둘 다" 입니다!** 
`select()` 함수의 가장 큰 매력은 소켓의 역할을 가리지 않고 이벤트(상태 변화)를 감지한다는 점입니다. 우리는 수신(`readfds`) 감시 목록에 두 종류의 소켓을 모두 넣습니다.

1. **서버 소켓 (Listen Socket)**:
   - **발생하는 이벤트**: 누군가 `connect()`를 시도함.
   - **의미**: "나한테서 `accept()`를 호출하면 멈추지(Blocking) 않고 즉시 새 클라이언트 소켓을 뽑아낼 수 있어!"
2. **클라이언트 소켓들 (Session Sockets)**:
   - **발생하는 이벤트**: 클라이언트가 패킷을 보냈거나, 혹은 접속을 정상적으로 끊음(FIN).
   - **의미**: "나한테서 `recv()`를 호출하면 멈추지 않고 즉시 데이터를 읽을 수 있어! (만약 0바이트를 리턴하면 접속 종료를 의미해)"

즉, `select()`가 깨어났을 때 이벤트가 발생한 소켓이 **서버 소켓**이라면 `accept()`를 호출하고, **클라이언트 소켓**이라면 `recv()`를 호출하는 식으로 분기(if-else) 처리를 하게 됩니다.

**Q. `readfds`는 읽을 대상이라 이해했는데, `writefds`는 언제 쓰나요? 보내는 건 굳이 이벤트가 필요 없지 않나요?**
**A. OS의 송신 버퍼(Send Buffer)가 꽉 찼을 때를 대비하기 위해 사용합니다!**

보통 `send()` 함수를 호출하면 데이터가 쑥 보내지는 것 같지만, 실제로는 우리가 넘긴 데이터를 **OS 커널 내부의 '송신 버퍼'로 복사**하는 것일 뿐입니다. 
만약 네트워크 상태가 안 좋거나 우리가 엄청난 양의 데이터를 쏴서 **OS의 송신 버퍼가 꽉 차버리면, `send()` 함수도 빈 공간이 생길 때까지 블로킹되어 멈춰버립니다!**

따라서 `writefds`에 소켓을 넣는다는 것은 OS에게 이렇게 묻는 것입니다.
**"지금 이 소켓의 송신 버퍼에 빈 공간이 있어? 내가 지금 `send()`를 호출해도 멈추지 않고 즉시 쏠 수 있니?"**

> **💡 추가 팁**: 논블로킹(Non-blocking) 모드로 설정된 소켓에서 `connect()`를 호출하면 즉시 리턴되는데, 이때 서버와 연결이 완전히 성공했는지를 확인하는 방법 역시 `writefds`에 이벤트가 뜨는지를 확인하는 것입니다.

**Q. 그러면 제가 예전에 `send()`를 걸어둔 게 있다는 걸 감지하는 건가요?**
**A. 아닙니다! `select()`는 우리 프로그램이 "보낼 데이터가 있는지"에는 전혀 관심이 없습니다. 오직 "OS 버퍼에 물리적인 여유 공간이 있는지"만 확인합니다.**

이 부분이 굉장히 많이 헷갈리는 포인트입니다.
만약 소켓을 만들자마자 `writefds`에 넣고 `select()`를 돌리면 어떻게 될까요? OS 송신 버퍼는 초기 상태에 텅텅 비어있으므로, `select()`는 **호출하자마자 "지금 당장 빈 공간 있어!" 라며 무한대로 즉시 리턴(이벤트 발생)해버립니다.** (CPU 100%의 원인)

그래서 실무에서는 `writefds`를 다음과 같이 제한적으로 사용합니다.
1. 평소에는 `writefds`에 아무것도 넣지 않습니다. 보낼 데이터가 생기면 그냥 `send()`를 냅다 호출합니다.
2. 만약 버퍼가 꽉 차서 `send()`가 `WSAEWOULDBLOCK`(버퍼 꽉참 에러)을 뿜어내며 실패하면?
3. **그제서야 해당 소켓을 `writefds`에 슬쩍 넣습니다.**
4. 시간이 지나 OS가 꽉 찬 버퍼의 데이터를 랜선을 통해 날려 보내고 '빈 공간'이 다시 생기면, 그때 `select()`가 `writefds` 이벤트를 띄워줍니다.
5. "아! 이제 다시 공간이 생겼구나!" 하고 아까 못 보낸 남은 데이터를 다시 `send()` 합니다.

---

**Q. 쓰기 관련 이벤트가 발생하면 `writefds`에 있는 '모든' 소켓에게 이벤트를 쏘는 건가요? 제가 예전에 막혔었는지 여부랑은 상관없이요?**
**A. 정확합니다! OS는 우리가 예전에 뭘 했는지(막혔는지)에 대해 전혀 관심이 없습니다. 오직 현재 물리적인 상태만 보고 배열을 "치워버리는(가지치기)" 역할만 합니다.**

`select()`의 핵심 동작 원리는 **"배열 가지치기(Pruning)"** 입니다.
우리가 `writefds`에 소켓 1, 2, 3을 넣어서 OS에 넘겨주면, OS는 다음과 같이 검사합니다.

* "소켓 1번 버퍼 지금 공간 있네? (목록에 유지)"
* "소켓 2번 버퍼 지금 꽉 찼네? (목록에서 삭제 ✂️)"
* "소켓 3번 버퍼 지금 공간 있네? (목록에 유지)"

검사가 끝나면 OS는 우리에게 **[소켓 1, 소켓 3]만 남은 배열을 돌려줍니다.** (이걸 우리가 `FD_ISSET`으로 하나하나 확인해서 살아남은 놈을 찾는 거죠!)
즉, 이벤트가 발생해서 "쏘는" 개념이라기보다는, 우리가 매번 "얘네들 쏠 공간 있어?" 하고 묶어서 주면, OS가 "공간 없는 애들은 지웠어. 살아남은 애들이 공간 있는 애들이야" 하고 답안지를 채점해서 돌려주는 **수동적인 상태 검사**에 가깝습니다.

따라서 우리가 평소에 아무 이유 없이(보낼 것도 없으면서) 빈 공간이 널널한 소켓을 `writefds`에 계속 넣어두면, OS는 채점할 때마다 "어, 얘 공간 있어!" 하고 매번 100점을 주어 살려두게 되고, 결과적으로 `select()`가 대기하지 않고 무한정 리턴되어 CPU 100%를 찍는 불상사가 생기는 것입니다.

**Q. 배열에서 지운다는 게 정확히 물리적으로 무슨 뜻인가요?**
**A. `select()` 함수가 우리가 넘겨준 변수의 메모리를 직접 덮어씌워 버린다(파괴한다)는 뜻입니다!**
우리는 `select(..., &readfds, ...)` 처럼 포인터(주소)를 넘겨줍니다. `select()` 함수는 검사를 마친 뒤, 조건(빈 공간 유무 등)을 만족하지 못하는 소켓들을 그 배열에서 아예 빼버리고(메모리를 조작해서) 함수를 종료합니다.
이 때문에 `select()`를 호출하고 나면 원본 `fd_set`이 훼손되므로, **반드시 `while` 루프를 돌 때마다 매번 `FD_ZERO`로 비우고 `FD_SET`으로 다시 소켓을 넣어주는 초기화 작업이 필수**입니다! (초보자들이 실무에서 가장 많이 하는 실수입니다)

**Q. 그러면 `select()`가 하는 일이 엄청 다양한 거 아닌가요?**
**A. 사실 본질은 딱 하나("상태 관찰")이지만, 감시하는 대상이 누구냐에 따라 의미가 달라질 뿐입니다.**
OS 입장에서는 그냥 "이 소켓의 버퍼나 큐에 뭔가 변화가 생겼나?"만 체크할 뿐입니다. 
- 대상이 **Listen 소켓 + `readfds`** 라면? -> "수신 큐에 뭔가 생겼어!" = **접속 요청(accept)이 왔구나!**
- 대상이 **Client 소켓 + `readfds`** 라면? -> "수신 버퍼에 뭔가 생겼어!" = **데이터가 왔구나(recv)! 혹은 끊겼구나!**
- 대상이 **Client 소켓 + `writefds`** 라면? -> "송신 버퍼에 빈 공간이 있어!" = **데이터 보낼 수 있구나(send)!**

**Q. 왜 무한정 리턴된다는 건가요?**
**A. `select()`는 "조건을 만족하는 소켓이 하나라도 있으면 즉시 스레드를 깨운다"는 특징 때문입니다.**
만약 송신 버퍼가 텅텅 비어있는(당장 데이터를 보낼 수 있는) 정상적인 소켓을 굳이 `writefds`에 넣었다고 가정해 봅시다. `select()`는 관찰을 시작하자마자 "어? 얘 지금 공간 널널하네! 조건 만족했으니 바로 깨워줄게!" 하고 0.00001초 만에 즉시 리턴해버립니다.
이게 `while(true)` 루프 안에 있다면 어떻게 될까요? 스레드가 쉴 틈 없이 깨어나서 무한 루프를 돌게 되고, 순식간에 CPU 점유율이 100%로 치솟게 됩니다. 반면 `readfds`에만 넣었다면, 클라이언트가 데이터를 보낼 때까지는 조건이 만족되지 않으므로 스레드가 깊이 잠들면서(Sleep) CPU 점유율을 0%로 착하게 유지합니다.

**Q. `FD_ZERO` 같은 건 C언어 시절부터 매크로로만 조작 가능했던 건가요? 굳이 매크로를 쓰는 이유가 있나요?**
**A. 운영체제(OS)마다 `fd_set`의 내부 구조가 완전히 다르기 때문입니다! 이를 소스 코드 레벨에서 호환시키기 위한 "눈속임(추상화)"입니다.**
- **Linux (POSIX)**: 파일 디스크립터(FD)가 0, 1, 2, 3... 처럼 작은 연속된 정수입니다. 그래서 Linux의 `fd_set`은 단순한 **비트마스크(Bitmask)** 입니다. (예: 3번 소켓 = 3번째 비트를 1로 켬). 매크로는 단순히 비트 연산(`|=`, `&=`)을 수행합니다.
- **Windows (Winsock)**: 소켓 핸들(`SOCKET`)이 연속된 숫자가 아니라 메모리 주소 같은 거대한 무작위 값입니다. 그래서 비트마스크를 쓸 수 없어, 내부적으로 **진짜 배열(`fd_array`)과 개수(`fd_count`)를 가진 구조체**로 재정의했습니다. Windows의 `FD_SET` 매크로는 사실 내부적으로 `for`문을 돌면서 배열 빈칸을 찾아 값을 추가하는 함수/코드로 치환됩니다.
즉, 프로그래머가 OS의 차이를 신경 쓰지 않고 똑같은 코드(`FD_SET`)를 쓰게 만들기 위해, 아주 오래전 C언어 시절부터 매크로를 이용해 내부 동작을 숨겨둔 역사의 산물입니다.

---

**Q. OS가 소켓을 처음 만들면 무조건 블로킹 모드인가요? 왜 명시적으로 논블로킹 전환 코드가 필요한가요?**
**A. 네, 소켓의 기본(Default) 상태는 무조건 "블로킹(Blocking)"입니다.**
블로킹 상태에서 OS 송신 버퍼가 꽉 찼을 때 `send()`를 호출하면, OS는 빈 공간이 생길 때까지 우리 프로그램의 메인 스레드를 아예 기절(Sleep)시켜 버립니다. 싱글 스레드 기반의 `select` 멀티플렉싱 서버에서 메인 스레드가 기절하면 1만 명의 손님이 모두 멈추는 대참사가 일어납니다.
따라서 OS에게 "버퍼가 꽉 차도 스레드 멈추지 말고 즉시 에러(`WSAEWOULDBLOCK`)를 뱉고 리턴해라!"라고 명시적으로 명령(`ioctlsocket(..., FIONBIO, ...)`)을 내려 논블로킹 모드로 바꿔주는 것입니다. (실무에서는 통신이 시작되기 전인 `accept()` 직후에 바로 세팅합니다)

**Q. 클라이언트 소켓마다 OS에서 송수신 버퍼를 따로따로 할당해주나요?**
**A. 네, 정확합니다! (1소켓 = 1쌍의 전용 버퍼)**
`accept()`로 새로운 클라이언트 소켓이 탄생할 때마다, OS 커널은 해당 클라이언트만을 위한 **전용 송신 버퍼(약 64KB)와 수신 버퍼(약 64KB)**를 독립적으로 생성합니다. 즉, 동시 접속자가 1만 명이라면 1만 개의 송신 버퍼와 1만 개의 수신 버퍼가 OS 메모리에 각각 따로 존재하게 됩니다. 이것이 TCP 네트워크 서버가 RAM 메모리를 많이 소모하는 주된 이유입니다.

---

**Q. 블로킹 소켓 상태로 에코 서버를 띄웠을 때 생길 수 있는 치명적 문제는 뭔가요?**
**A. 악의적인 클라이언트 하나가 전체 서버를 마비(Freezing)시킬 수 있습니다.**
만약 어떤 클라이언트가 데이터를 보내기만 하고 절대 수신(읽기)하지 않는다면, 클라이언트의 수신 버퍼가 꽉 차고 이어서 서버의 송신 버퍼까지 꽉 차게 됩니다. 이때 서버가 에코를 위해 블로킹 소켓에 `send()`를 호출하면 버퍼에 공간이 생길 때까지 메인 스레드가 영원히 잠들어버립니다. 이 때문에 `select()` 모델을 쓰더라도 **반드시 소켓을 논블로킹(`ioctlsocket`)으로 강제 전환**해 두어야, 다른 정상적인 클라이언트들이 피해를 보지 않습니다.

**Q. OS 송신 버퍼는 64KB인데, 어떻게 190KB 넘게 `send()`를 성공시켰나요?**
**A. `send()` 성공은 "네트워크로 전송 완료"가 아니라, "TCP 파이프라인에 데이터 밀어넣기 성공"을 의미하기 때문입니다.**
TCP 통신은 거대한 파이프 구조입니다. `[서버 송신 버퍼(64KB)] -> [네트워크] -> [클라이언트 수신 버퍼(약 128KB)]`. 서버가 냅다 데이터를 쏘면, 이 데이터들은 클라이언트의 수신 버퍼부터 차곡차곡 쌓입니다. 클라이언트 수신 버퍼가 가득 차면 그제서야 서버 측 송신 버퍼에 데이터가 고이기 시작하고, 결국 양쪽 버퍼가 100% 꽉 찼을 때에야 비로소 `send()`가 `WSAEWOULDBLOCK` 에러를 뿜어냅니다. 즉, 보낸 데이터양 = 양쪽 OS 버퍼 크기의 합입니다.

**Q. `writefds`는 언제 어떻게 활용하나요?**
**A. 논블로킹 소켓에서 `send()`가 `WSAEWOULDBLOCK` 에러를 뱉었을 때만 사용합니다.**
평소에는 빈 공간이 넘쳐나므로 소켓을 `writefds`에 넣으면 CPU 100% 무한 루프에 빠집니다. 에러가 발생하여 통로가 막혔을 때만 해당 소켓을 `writefds`에 살짝 넣고 대기합니다. 시간이 지나 클라이언트가 데이터를 소화해서 OS 버퍼에 빈 공간이 다시 생기면, `select()`가 이벤트를 띄워주며 "이제 다시 쏠 수 있어!" 라고 알려주는 기믹으로 활용합니다.
