# Module 13: 서버 아키텍처 기초 - Thread Pool 모델 (동기식 다중 처리)

## 🎮 실무 프로젝트 상황 (Why do we need this?)

Module 12에서 우리는 클라이언트와 연결을 맺고(TCP) 패킷을 주고받는(UDP) 방법을 배웠습니다.
가장 단순한 형태의 서버는 **"클라이언트가 접속할 때마다 새로운 `std::thread`를 생성하여 전담 마크를 맡기는 방식(Thread-per-Client)"**이었습니다.

하지만 이 방식에는 치명적인 문제가 있습니다:
1. **스레드 생성 비용**: OS에서 스레드를 생성하고 삭제하는 것은 매우 무거운 작업입니다. 수천 명이 동시에 접속한다면? 서버가 스레드 만들다가 죽어버립니다.
2. **컨텍스트 스위칭(Context Switching) 폭발**: CPU 코어 수(예: 8코어)보다 스레드 수(예: 1000개)가 훨씬 많으면, CPU는 누구 일을 먼저 처리할지 스레드를 교체하는 데 시간을 다 씁니다 (오버헤드).
3. **메모리 고갈**: 스레드 하나당 기본적으로 약 1MB의 스택 메모리를 할당받습니다. 1만명이면 10GB의 RAM이 그냥 스레드 공간으로 증발합니다.

**💡 해결책**: "미리 정해진 수(예: CPU 코어 수)의 스레드(일꾼)만 만들어두고, 일이 들어오면 큐(Queue)에 쌓아둔 뒤 일꾼들이 하나씩 가져가서 처리하게 하자!"
이것이 바로 **Thread Pool(스레드 풀)**의 핵심 아이디어입니다.

---

## 🧠 이론 설명: Thread Pool의 구조

Thread Pool은 크게 세 가지 요소로 구성됩니다.

1. **Worker Threads (일꾼)**: 프로그램이 시작될 때 미리 생성되어 대기 상태로 있는 스레드들입니다. 보통 CPU 코어 개수에 맞춰 생성합니다.
2. **Job Queue (작업 대기열)**: 처리해야 할 일(게임 패킷, 이동 연산 등)들이 줄을 서서 기다리는 곳입니다. 여러 일꾼이 동시에 큐에 접근하므로 `std::mutex`로 보호되어야 합니다.
3. **Condition Variable (조건 변수)**: 일꾼들을 재우고 깨우는 알람시계입니다. 큐가 비어있으면 일꾼을 재우고(Sleep), 새로운 일이 들어오면 깨워서(Wake up) CPU 낭비를 막습니다.

## 🔬 하드웨어 검증: 스레드 재사용 눈으로 확인하기

스레드가 진짜로 재사용되는지 눈으로 확인해볼 수 있는 간단한 개념 증명(PoC)입니다.
(이 코드는 눈으로 흐름을 파악하기 위한 슈도 코드에 가깝습니다. 실습에서 직접 만들어 볼 것입니다!)

```cpp
#include <iostream>
#include <thread>
#include <vector>
#include <queue>
#include <mutex>
#include <condition_variable>
#include <functional>

// 작업 큐와 동기화 객체들
std::queue<std::function<void()>> jobQueue;
std::mutex queueMutex;
std::condition_variable cv;
bool bStopPool = false;

// 일꾼(Worker) 스레드가 영원히 반복하는 함수
void WorkerThread() {
    while (true) {
        std::function<void()> job;
        
        { // 1. 자물쇠를 걸고 큐에 접근
            std::unique_lock<std::mutex> lock(queueMutex);
            
            // 2. 일이 들어오거나 종료될 때까지 대기 (CPU 점유율 0%)
            cv.wait(lock, []() { return !jobQueue.empty() || bStopPool; });
            
            if (bStopPool && jobQueue.empty()) return; // 퇴근
            
            // 3. 일거리 챙기기
            job = std::move(jobQueue.front());
            jobQueue.pop();
        } // 자물쇠 해제

        // 4. 일 처리 (스레드 ID 출력하여 어떤 일꾼이 처리했는지 확인)
        std::cout << "[Thread " << std::this_thread::get_id() << "] 이 일을 처리합니다!\n";
        job(); 
    }
}
```

**[실행 결과 예상]**
작업 100개를 던져도, 스레드 ID는 딱 4개(만약 4개만 만들었다면)만 반복해서 출력됩니다. 즉, 매번 새로운 스레드를 만들지 않고 기존 스레드가 작업을 순환하며 처리하고 있음을 증명합니다.

## 🙋‍♂️ Q&A: 깊이 알아보기

**Q1. 왜 `std::lock_guard` 대신 `std::unique_lock`을 사용하나요?**
* **A.** `std::lock_guard`는 스코프(`{ }`)를 벗어날 때까지 무조건 자물쇠를 잠그고 있습니다. 중간에 임의로 자물쇠를 풀 수 없습니다.
* 반면, 스레드 풀의 일꾼들은 일이 없을 때 대기(Sleep)해야 합니다. 내가 자고 있는 동안 다른 스레드(main 등)가 큐에 새로운 일거리를 넣을 수 있어야 하므로, **"자물쇠를 잠깐 풀고 자러 가야"** 합니다.
* `std::unique_lock`은 `lock_guard`처럼 안전하게 동작하지만, **수동으로 `unlock()`과 `lock()`을 할 수 있는 유연함**을 가집니다. 뒤에 나오는 `condition_variable::wait()`가 이 유연함을 필요로 하기 때문에 짝꿍으로 사용해야 합니다.

**Q2. `condition_variable` (조건 변수)는 정확히 뭔가요?**
* **A.** 스레드들을 **효율적으로 재우고 깨우는 "알람 시계"** 입니다.
* 만약 조건 변수가 없다면, 일꾼은 "큐에 일 있나? (없네)", "일 있나? (없네)" 하면서 무한 루프(`while(true)`)를 미친 듯이 돌며 큐를 확인해야 합니다. 이를 **Busy Waiting(바쁜 대기)**라고 하며, CPU 점유율을 100%로 낭비하게 만듭니다.
* `cv.wait(lock, 조건)`을 호출하면 다음과 같은 마법이 일어납니다:
  1. 조건이 거짓(큐가 빔)이면, **들고 있던 자물쇠(`lock`)를 자동으로 풀고 스레드를 깊은 잠(Sleep)에 빠뜨립니다.** (CPU 점유율 0%)
  2. 누군가 큐에 일을 넣고 알람을 울리면 (`cv.notify_one()`),
  3. 자던 스레드 중 하나가 깨어나서 **다시 자물쇠(`lock`)를 낚아채고** 일거리를 꺼내갑니다.

**Q3. `cv.wait()` 내부에서 자물쇠를 풀 수 있으려면 반드시 `unique_lock`이어야만 하나요?**
* **A.** 네 맞습니다! C++ 표준에서 `condition_variable::wait()` 함수는 파라미터로 오직 `std::unique_lock<std::mutex>&` 타입만 받도록 엄격하게 규정되어 있습니다. `lock_guard`를 넘기면 `unlock()` 기능이 없기 때문에 컴파일 에러가 발생합니다.

**Q4. `cv.wait(lock, []() { return 조건; })` 에서 두 번째 인자인 조건식의 의미는 뭔가요?**
* **A.** 이 조건은 스레드가 **"일어나서 다음 코드를 실행해도 될까?"**를 판단하는 기준입니다.
* 동작 방식: **"조건이 참(True)이면 깨어나서 아래 코드로 진행하고, 거짓(False)이면 다시 자물쇠를 풀고 자라!"**
* 우리 코드의 조건: `!jobQueue.empty() || bStopPool`
  * 해석: "큐에 일거리가 들어왔거나(`!empty()`), 혹은 스레드 풀이 종료(퇴근) 명령(`bStopPool`)을 받았다면 깨어나서 진행해라!"
  * 위 조건이 둘 다 아니면(큐도 비었고 퇴근도 아님) 결과는 `false`가 되어, 다시 꿀잠에 빠집니다.
* **왜 굳이 조건을 또 적어주나요?**
  * OS의 구조적 한계로 인해, 알람(`notify`)이 울리지 않았는데도 스레드가 뜬금없이 깜짝 놀라 깨어나는 현상(**Spurious Wakeup, 가짜 깨어남**)이 발생할 수 있습니다. 
  * 만약 조건식이 없다면 가짜로 깨어났을 때 빈 큐에서 `jobQueue.front()`를 꺼내려다가 프로그램이 터지겠죠. 그래서 "진짜 깨어나도 되는 상황인지" 확실히 검증하기 위해 두 번째 인자로 조건을 달아주는 것입니다.

**Q5. `cv.notify_one()`을 부를 때, `cv`는 일꾼이 몇 명인지 어떻게 알고 딱 "한 명만" 부를 수 있나요?**
* **A.** 사실 `condition_variable` 자체는 우리가 만든 `std::vector<std::thread>`(일꾼 목록)가 몇 명인지 전혀 모릅니다! 
* 비밀은 **운영체제(OS)**에 있습니다.
* 스레드가 `cv.wait()`를 호출하며 잠들면, OS는 해당 스레드를 **이 `cv` 전용 '대기실(Wait Queue)'**에 명단과 함께 집어넣고 재웁니다.
* 그래서 누군가 `cv.notify_one()`을 호출하면, OS가 대기실 명부를 보고 "음, 제일 오래 잔 애(혹은 우선순위가 높은 애) 한 명만 깨워서 내보내야지" 하고 **스스로 알아서 한 명만** 잠에서 깨워(Ready 상태로 변경) 줍니다.

**Q6. "락을 걸어서 상호 배제를 하면, 다른 스레드는 나중에 순서대로 읽게 되니까 굳이 동기화를 안해도 자연스럽게 최신 값을 보게 되는 것 아닌가요?"**
* **A.** 프로그래머의 직관으로는 아주 타당한 생각이지만, 하드웨어(CPU)와 컴파일러의 배신 때문에 그렇지 않습니다!
* 시간 순서대로 완벽하게 `[쓰기 완료] 👉 [나중에 읽기]` 로 동작했더라도, 두 스레드가 서로 다른 CPU 코어에서 실행 중이라면, 읽기를 수행하는 코어는 **자기 자신의 L1 캐시**에 남아있는 과거의 값을 읽어버립니다.
* 또한 컴파일러는 루프 안에서 변수가 수정되지 않는다고 판단하면, 매번 메모리를 읽지 않고 CPU 레지스터에 값을 고정해버리는(캐싱) 최적화를 수행합니다.
* **`std::mutex`의 진짜 역할**은 단순히 상호 배제뿐만 아니라, **"지금부터 캐시나 레지스터를 믿지 말고 무조건 실제 메인 메모리(RAM)에서 최신 데이터를 새로 긁어와!" (Memory Barrier)** 라고 컴파일러와 CPU에게 호통을 치는 역할까지 동시에 수행합니다.
* 따라서 락을 걸어야만 깨어난 일꾼들이 락을 획득하면서 캐시를 새로고침하여 완벽하게 최신 값을 보장받을 수 있습니다.
